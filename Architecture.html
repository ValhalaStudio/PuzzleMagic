What this is

A block-placement puzzle in the Woodoku family, built with Unreal Engine 5.8 and C++. It targets iPhone (landscape only, touch first) and runs on Windows.

You drag pieces from a tray of three onto a board from 4×4 up to 8×8. Any route clears: a chain of tiles, each pointing at the next, from one side of the board to the opposite side. The rules live in one plain object, UPuzzleManager, which changes state the moment a piece lands and broadcasts events. What you see and hear follows later, timed to the animations: the game mode turns rule events into sound, haptics, camera shake and UI, and the cathedral reads your luck to decide how dark the room gets.

Board

Width and height each from 4 to 8 cells. A tray of 3 pieces plus HOLD, drawn from 12 shapes.

Combo (option, off by default)

A clear starts a combo that survives 3 placements without a clear. Multi-line clears climb faster and multiply the score.

Move budget (off, MVP)

Each piece costs a move; clears refund moves. A round starts with 30 and ends when they run out or no piece fits. With the budget off, only a full board ends the round.

Relics (option, off by default)

One every 3 combo steps, at most 3 of each. Holy Light purges a 3×3 area; Reroll replaces the tray.

Luck (option, off by default)

Starts at 20. +6 per clear, −20 for Holy Light, −12 for Reroll. It lights the candles in the cathedral: when it runs out, the dark wakes.

Score

2 per cleared tile and 15 per route, plus 10^n for a route n tiles longer than the straight line across (5^n between neighbouring sides), capped at 100,000 per route. Placing a piece scores nothing. Beat your saved best; a demo mode lets a greedy bot play.

Presentation

A Lumen-lit cathedral on PC, a dread layer that wakes as luck runs out, an interface built in C++, a synthesized Gregorian score and a MetaSound ambience.

Architecture

Input reaches the rules, the rules change the board and announce what happened, and the game mode decides how it looks and sounds.

Decisions that shape the code

  1. Rules never touch visuals. UPuzzleManager is a UObject with no rendering. It updates the board state immediately and broadcasts events; the board plays animations with delays, and the game mode times sound, haptics and UI to them.
  2. The UI is code. UPuzzleHUDWidget builds every widget in C++ from two materials (enamel panel, embossed icon) and two fonts. Nothing lives in a Widget Blueprint, so the UI diffs and reviews like the rest.
  3. Every asset comes from a script. Materials are HLSL custom nodes written by Python in the editor, sounds are synthesized, meshes are procedural or scripted in Blender, and textures come from ComfyUI.
  4. Rebuildable assets load at run time. An asset held by a C++ constructor (ConstructorHelpers) is rooted inside the editor commandlet, and rebuilding it there crashes. Newer assets use LoadObject so their scripts can rebuild them in place.
  5. All tiles share one mesh. MeshBuffers builds the tile once as a realtime mesh and every tile's component points at it: one set of GPU buffers for the whole board.
  6. PC gets Lumen; iPhone gets the mobile renderer. Lumen doesn't run on iOS in 5.8, so the phone look has to be authored for the mobile renderer.
  7. Visual changes are checked in screenshots. Logs stayed clean while the camera faced the sky and while meshes rendered inside out, so every visual change is verified with a capture of the running game.

A move, end to end

What happens between dropping a piece and the last popup fading. Times come from AGridManager::ArriveDuration (0.5 s) in the code.

Start-up, in order

  1. APuzzleGameMode::StartPlay loads or creates the save (UPuzzleSaveGame::LoadOrCreate) and creates the rules.
  2. It spawns AGridManager, APuzzleInputHandler and AGothicEnvironment, binds the rules to the board and gives the input handler both.
  3. It binds the six rule events, creates the demo bot and frames the camera on the board and tray.
  4. It starts the music playlist: the chant twice, then the organ piece, crossfaded.
  5. It reads the launch flags (see Run & tune) and opens the menu, with How to Play on the very first launch, or goes straight to a demo or a level.

Meanwhile AGothicEnvironment::BeginPlay builds the wall, stained glass, piers, flagstones, mist and candles, attaches the convolution reverb to the SM_Cathedral submix and builds the dread layer: tentacles, eyes, fog volumes, motes, the madness post-process and the MetaSound ambience.

Board size

The board is any width and height from 4 to 8 cells, so the game can ask for harder or easier courses later.

An earlier version used a 9×9 board where 3×3 boxes also cleared, because boxes only tile a board whose side is a multiple of three. Dropping boxes removed a whole layer of rules (box shading, box goals) and leaves routes as the only way to clear. AGridManager::SetGridSize rebuilds the frame, slots, tray and collision for a new size, and -grid=WxH picks one at launch.

  • Holy Light purges a 3×3 area around a chosen cell, with its centre clamped to cells 1 to 6 so it always stays on the board.
  • Checkerboard slots. Slots alternate indigo and burgundy per cell (AGridManager::BuildBoardVisuals), so the grid reads at a glance.
  • The bot aims Holy Light at the densest 3×3 area (FindDensestArea).

It also fits the phone. At 8 cells and 90 units each the largest board is 720 units across, inside the landscape canvas (1080 units tall), with the tray below the board and the score at the top right. The tray row is wider than a 4-cell board, so small boards are framed by the tray.
